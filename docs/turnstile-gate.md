# Page verification on Cloudflare Workers

The Worker checks page requests before Astro, including static HTML. A successful Turnstile verification permits one request for the same hostname, path and query using a non-secret challenge selector; a new navigation or refresh requires another challenge. API routes and the explicit asset and framework protocol paths remain outside this gate. The normal local Astro dev server bypasses the gate only for localhost, its subdomains (such as `shop.localhost`), and loopback IPs when both keys are absent; the production build always fails closed when a binding is missing.

Before deployment, configure a **Managed** Turnstile widget and supply `TURNSTILE_SITE_KEY` (a Worker variable) and `TURNSTILE_SECRET_KEY` (a Worker secret). No keys are included in this repository. Authorize each public root or standalone hostname in the widget; authorizing a root covers its subdomains. Route every intended public hostname, including wildcard storefront hostnames, through this Worker and ensure HTTPS is active. The checked-in Wrangler configuration adds the `TURNSTILE_CHALLENGES` Durable Object and SQLite migration; deploy that migration with the Worker. Do not enable a shared cache rule that bypasses the Worker or overrides its no-store response. The Worker must run first for assets as configured.

The [environment template](../.env.example) lists the settings for local development. On Cloudflare, use **Workers & Pages → your Worker → Settings → Variables and Secrets**. Set `TURNSTILE_SITE_KEY` as **Text** and `TURNSTILE_SECRET_KEY` as **Secret**. The checked-in `keep_vars: true` setting preserves dashboard variables such as the site key on subsequent Wrangler deployments. Wrangler retains the encrypted secret separately. If the dashboard offers a Wrangler snippet after you save these bindings, keep the Turnstile values in the dashboard. [Wrangler configuration](https://developers.cloudflare.com/workers/wrangler/configuration/#source-of-truth)

Each page navigation, including redirects and refreshes, incurs a separate challenge. Issuance and refresh use a short-lived signed context without Durable Object storage; a successful strict Siteverify response initializes the one-use Durable Object proof. Up to eight outstanding challenges per browser and host are accepted; they expire after five minutes. Wait for expiry if the limit is reached. The Worker runs for static assets as well, including the large frame sequence, so asset-heavy visits can incur many Worker invocations. This can affect usability, indexing and cost. The gate depends on JavaScript and Cloudflare availability. Browser history restoration may show an already-rendered page without a network request; server-side checks cannot intercept a browser's back-forward cache. The Cloudflare test keys do not return matching custom action and cData, so they cannot prove a successful production-style verification; use a real widget on an authorized test hostname for that check.

References: [Astro custom Worker entrypoint](https://docs.astro.build/en/guides/integrations-guide/cloudflare/), [Cloudflare Worker-first assets](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/), [Turnstile validation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/), [hostname management](https://developers.cloudflare.com/turnstile/additional-configuration/hostname-management/) and [testing](https://developers.cloudflare.com/turnstile/troubleshooting/testing/).

A successful challenge adds a temporary selector to its continuation URL. The Worker forwards the original URL to Astro and removes the selector from HTML page addresses with a same-origin script, preserving the fragment. This prevents an ordinary refresh from consuming another tab’s proof. Redirects remain controlled by Astro. Plain-text or empty error responses cannot run the cleanup script, so their address can retain the inert selector until the visitor navigates. The selector alone grants no access.
